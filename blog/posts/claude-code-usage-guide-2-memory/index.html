Claude Code 使用指南（中）：记忆系统与项目上下文

2026-07-24 · 预计阅读 12 分钟 AI学习

上篇讲了命令和配置，本篇聚焦 Claude Code 最核心的能力——记忆系统。理解 CLAUDE.md 和 /memory 的区别，学会写好项目记忆文件，是"用好 Claude Code"和"只会用 Claude Code"的分水岭。

一、两层记忆体系

Claude Code 有两层独立的记忆，各司其职：

CLAUDE.md /memory
存哪里 项目根目录 本地用户目录
作用范围 当前项目 所有项目
谁看得到 团队共享（进 Git） 只有你
适合存什么 项目规则、流程、约定 个人偏好、习惯、通用参考
自动加载 每次会话自动加载 自动注入

一句话区分：CLAUDE.md 是"这个项目怎么干"，/memory 是"我喜欢怎么干"。

二、CLAUDE.md — 项目记忆文件

是什么

/init 命令会自动生成一个 CLAUDE.md 放在项目根目录，你也可以手动创建和编辑。每次新开对话，Claude Code 会自动读取它，作为理解项目的"说明书"。

什么时候需要它

  • 项目有特定的目录结构，AI 需要知道文件怎么组织的
  • 有固定的操作流程和规范（比如构建、部署、测试）
  • 有命名约定、代码风格、架构约束
  • 有些操作你知道会反复做，想把流程写下来自动化

没有 CLAUDE.md，AI 每次都要从零开始理解你的项目。有了它，AI 一上来就知道项目是干什么的、文件怎么放的、操作流程是什么。

怎么写——核心原则

一个判断标准：CLAUDE.md 里应该写"不会变的事"，不是"会变的事"。

应该写（长期稳定） 不应该写（临时可变）
项目定位和用途 当前正在做的具体任务
目录结构说明 今天改了哪个文件
操作流程和步骤 本次会话的临时决定
命名规范和约定 下一篇文章的标题
技术栈和工具路径 Bug 修复的临时记录
已知的坑和解决方案 临时的笔记草稿

实际案例：本项目的 CLAUDE.md

拿你现在看到的这个 Hugo 博客项目举例。它的 CLAUDE.md 结构是这样的：

## 工作原则
- 先读再改
- 先计划再执行
- 遵守工具流

## 项目定位
双仓库关系（hugo-blog ↔ GitHub Pages）

## 目录结构
各目录的用途说明

## 笔记生命周期
私有 ↔ 公开的完整流程

## 公开博客规范
Frontmatter 模板、八大类、标题层级、图片规范

## 操作流程
流程 A（私有→公开）/ 流程 B（直接新建）/ 流程 C（写私有）

## 常用命令
编译、部署、排错命令速查

## 发布后验证与排错
常见问题和解决方案

这个结构覆盖了 AI 需要知道的全部"不变信息"——项目是什么、结构怎么放、怎么做发布、出问题怎么排查。每次你让我发布文章，我不需要重新问"slug 放哪里"“分类有哪些"“编译命令是什么”，CLAUDE.md 都写好了。

写作技巧

技巧一：用命令式语气

CLAUDE.md 是给 AI 看的指令，不是给人看的教程。用"先读再改"而不是"建议你先读文件再修改”。明确、直接、不含糊。

# 好
先读再改：修改文件前必须先阅读当前内容

# 不好（太温和）
建议在修改文件之前，最好先看一下文件的当前内容

技巧二：列出具体步骤

模糊的指令 AI 可以理解但不一定执行一致。具体的步骤 AI 会严格遵循。

# 好
Step 1: 在 posts/ 下创建 slug 目录
Step 2: 复制笔记内容
Step 3: Frontmatter 转换（tags→categories，加 slug/readingTime，删 private/updated）

# 模糊
发布时记得处理好 frontmatter

技巧三：附上模板和命令

AI 擅长填模板和执行命令，但不擅长凭空猜测格式。把模板、命令直接写在 CLAUDE.md 里。

## Frontmatter 模板
---
title: "中文标题"
slug: "english-slug"
date: 2026-06-07
categories: ["AI学习"]
readingTime: 8
---

## 常用命令
Hugo 编译：cd hugo-blog && /tmp/hugo/hugo
标题批量后移：sed -i 's/^# /## /g; ...'

技巧四：记录踩过的坑

你遇到过的问题、解决方案，写在 CLAUDE.md 的"排错"部分。下次出同样的问题，AI 直接知道怎么处理，不用再排查一遍。

## 常见问题速查
1. 首页看不到新文章/404 → 检查 HTML 注释是否包裹了 <article>
2. 侧边栏缺少新分类 → 同步更新三处文件
3. Git push 成功但未更新 → GitHub Pages 有 1-2 分钟部署延迟

保持更新

CLAUDE.md 不是写一次就完了。项目规则变了、流程改了、发现了新的坑，都要同步更新。一个过时的 CLAUDE.md 比没有 CLAUDE.md 更糟糕——AI 会按照错误的规则执行。

更新时机：

  • 项目结构变了（新增目录、重构）
  • 操作流程改了（新的部署方式、新的工具）
  • 发现了新的常见问题
  • 新增了分类、规则、约定

CLAUDE.md 应该多长

没有硬性限制，但实用原则是：足够详细让 AI 不出错，足够精简让一次对话加载得完。通常 100-300 行比较合适。太短 AI 缺少信息容易出错，太长占用过多上下文。

三、/memory — 个人持久化记忆

是什么

/memory 存储的是跨项目的个人偏好和参考信息。它不是某个项目的专属，而是你自己的"AI 使用档案"。

与 CLAUDE.md 的互补关系

CLAUDE.md                          /memory
   ↓                                  ↓
"这个博客项目怎么发布文章"          "我喜欢中文输出，先计划再动手"
   ↓                                  ↓
跟着项目走（进 Git）               跟着你走（所有项目通用）

实际效果：你在这篇博客项目里设置的 CLAUDE.md，换到薪酬审阅工具项目里是看不到的——每个项目有自己的 CLAUDE.md。但 /memory 里的偏好设置，在哪个项目里都生效。

适合存什么

  • 输出偏好：“默认用中文思考和输出”
  • 工作风格：“非简单操作先出方案再动手”
  • 常用参考：外部资源的 URL、账号信息等
  • 跨项目经验：在多个项目中验证过的通用技巧

不适合存什么

  • 某个项目特有的规则 → 放 CLAUDE.md
  • 临时的一次性信息 → 放当前对话
  • 代码实现细节 → 放代码注释

四、第三层记忆——对话历史

除了 CLAUDE.md 和 /memory，还有一层"隐式记忆"：当前对话的上下文。

每次对话里讨论过的内容、做过的决定、改过的文件，AI 都能在本次会话中记住。但这层记忆有两个限制：

  1. 不跨会话：新开一个对话，之前的上下文不继承（除非写进了 CLAUDE.md 或 /memory）
  2. 有长度限制：对话太长时会触发 /compact 压缩，部分细节会丢失

什么该写进持久记忆，什么留在对话里

信息类型 放哪里 原因
“下次发布文章时，备注里写一句话摘要” CLAUDE.md 反复用到
“这五篇文章我确认要发布” 留在对话 一次性决定
“我发现 sidebar 漏了分类链接，已修复” CLAUDE.md 的排错区 下次可能再遇到
“帮我把这篇移到 _private” 留在对话 单次操作

一个简单的判断标准：如果你觉得"下次 AI 应该自动知道这个"，就写进持久记忆。

五、实战：建立一个有效的记忆体系

以你自己的 Hugo 博客项目为例，理想的三层记忆分工：

CLAUDE.md（已完成）

  • 项目定位、目录结构
  • 发布流程（三条）
  • Frontmatter 规范、八分类
  • 常用命令、排错速查

/memory（可补充）

  • 默认中文输出（已有）
  • 先计划再执行的偏好（已有）
  • 发布博客时提醒更新 CLAUDE.md 的排错区（如果有新的坑）

对话历史

  • 当前要发布哪几篇
  • 具体的文章内容讨论
  • 临时的格式调整

六、小结与下篇预告

中篇的核心要点：

  1. CLAUDE.md 是项目的大脑——存规则、流程、约定，每次会话自动加载
  2. /memory 是你的使用档案——跨项目生效，存个人偏好
  3. 写 CLAUDE.md 的诀窍：命令式语气、具体步骤、附带模板、记录踩坑、保持更新
  4. 判断标准：反复用到 → 写进持久记忆；一次性 → 留在对话
